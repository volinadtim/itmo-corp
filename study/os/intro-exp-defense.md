# Шпаргалка к защите ЛР 1 (intro-exp)

Стенд: Intel i5-11400F (6 ядер / 12 потоков, 2.6 ГГц, Turbo off), 32 ГБ DDR4-3200,
NVMe Kingston SNV3S1000G, Ubuntu 24.04.5, ядро 7.0.0-31-generic.
Данные: 360 запусков, ветка `lab-intro-exp`, коммит `3eef271`.

## 1. Что сделано

Полный факторный план: два обходчика × две топологии × холодный/тёплый кэш ×
чтение/запись = 16 конфигураций.

- **Данные.** Два графа по 256 МБ, seed 427, 11 184 809 вершин по 24 байта.
  Локальный: `--topology chain -b 0 --min-step-pages 0`. Случайный: параметры по умолчанию.
- **Изоляция.** governor `performance`, Turbo Boost выключен, `taskset -c 2`,
  `nice -n -5`, машина простаивает.
- **Кэш.** Холодный — `sync` + `drop_caches` перед каждым запуском.
  Тёплый — один прогрев в начале серии.
- **Серии.** N = 30 для чтения, 15 для записи. Первые 3 повтора отброшены как
  прогревочные (решение принято до просмотра данных). Интерливинг: в каждом
  повторе все 4 конфигурации подряд.
- **Статистика.** Среднее, СКО, CV, 95% ДИ по t-распределению, оценка нужного N.

## 3. Механизмы

**Почему у read sys-время — две трети?** `lseek` + `read` на каждую вершину:
11 184 809 × 2 ≈ 22.4 млн системных вызовов. Каждый — переход в режим ядра,
проверка аргументов, копирование 24 байт. Диск тут почти ни при чём.

**Почему у mmap 2807 major faults, а у read всего 2?** У `read()` данные копирует
ядро по явной просьбе, промахов страниц в адресном пространстве процесса нет.
У `mmap()` файл отображён, но не загружен: первое обращение к отсутствующей
странице — major fault и подъём с диска. Minor fault — страница уже в page cache,
её нужно лишь добавить в таблицу страниц процесса.

**В файле 65 536 страниц, почему промахов ≈ 4.4 тыс.?** Ядро на один промах
отображает окно соседних страниц (fault-around, по умолчанию до 16) плюс работает
readahead. 65 536 / 16 ≈ 4 096 — порядок совпадает с наблюдаемыми 4 418.

**Почему при записи у mmap 70 тыс. minor faults?** Страница отображается сначала
на чтение; первая запись вызывает отдельное нарушение доступа, ядро помечает
страницу грязной. Два события на страницу вместо одного.

**Почему у read seq ≈ rand, а у mmap разница 1.7–2.4 раза?** Время read-версии
определяется числом системных вызовов, а оно одинаково при любой топологии.
У mmap системных вызовов нет, поэтому видно именно работу с памятью.

**Гипотеза «на холодном кэше эффект сильнее» не подтвердилась.** У mmap отношение
rand/seq на тёплом кэше выше (2.40), чем на холодном (1.74). Переход к холодному
кэшу добавляет обеим конфигурациям примерно одинаковое время на подъём 256 МБ
с NVMe — общее слагаемое разбавляет отношение. Абсолютная разница почти не
меняется (0.56 против 0.59 с). Вывод: различие порождается промахами страниц и
TLB, а не ожиданием диска.

**Значит, mmap быстрее read?** Нет. Программы делают разный объём работы: 22 млн
мелких системных вызовов против одного. При чтении блоками по 64 КБ разрыв
сократился бы в разы. Цена mmap: `SIGBUS` вместо кода возврата при ошибке
ввода-вывода, непредсказуемый момент обращения к диску, вытеснением управляет
ядро. Поэтому СУБД держат свой буферный пул поверх `pread()`.

## 4. Методика

**Доверительный интервал:** среднее ± t(0.975, n−1) · s / √n, где s — выборочное
СКО с делителем n−1. t-распределение, а не нормальное, потому что дисперсия
оценивается по той же выборке и n невелико. Смысл: 95% таких интервалов накроют
истинное среднее.

**Почему N = 30?** Оценка n ≥ (z·s / (δ·x̄))² для точности 2% даёт единицы запусков.
30 взято с запасом. Увеличение сузит интервал как 1/√n, но выводы не изменятся:
систематические факторы уже вносят больше, чем случайный разброс.

**Зачем интерливинг?** При блочном порядке дрейф (нагрев, фоновые задачи) целиком
сместил бы одну конфигурацию. При чередовании он размазывается по всем четырём
и попадает в разброс, а не в смещение.

**Почему отброшены ровно 3 повтора?** Прогрев непрогретой системы. Число выбрано
до просмотра результатов — иначе отбрасывание превращается в подгонку.

**Почему не `--no-cache`?** На Linux он реализован через `O_DIRECT`, который требует
выравнивания буфера, смещения и длины на размер логического блока (для этого NVMe —
512 Б, подтверждено `smartctl`). Заголовок читается как 40 байт в невыровненный
буфер на стеке → `EINVAL` → «Failed to read header». Проверено `strace`.
Поэтому холодный кэш — внешним `drop_caches`, одинаково для обоих обходчиков.

**Зачем фиксировать частоту и выключать Turbo?** Turbo держит высокую частоту, пока
процессор холодный, — первые запуски систематически быстрее. `powersave` меняет
частоту по нагрузке. С `performance` и выключенным Turbo частота постоянна (2.6 ГГц).

**Почему ядро 2, а не 0?** На CPU 0 идёт основная масса прерываний. Включён SMT:
пары (N, N+6) делят физическое ядро. CPU 2 выбран так, чтобы сосед CPU 8 оставался
свободным.

**Обоснование размера 256 МБ.** При 32 ГБ RAM файл целиком помещается в page cache
(нужно для тёплого режима), в холодном честно читается с NVMe, обход длится
секунды — время не тонет в шуме. Swap не задействуется.

## 5. Слабые места

### Аномалия: тёплая запись, seq медленнее rand
20.30 с против 15.83 с при CV 0.25% и 0.16% — не случайность.
Гипотеза: обратная запись грязных страниц. При локальной записи грязные страницы
образуют протяжённые области, и `balance_dirty_pages` притормаживает процесс
раньше. Второй фактор — порядок серий: тёплая шла сразу после холодной.
Проверка: `sync` и пауза между сериями, снятие `Dirty`/`Writeback` из
`/proc/meminfo`, варьирование `vm.dirty_ratio`. В отчёте зафиксировано как есть.

### Параметры README не дают контраста топологий
`--topology chain` лишь форсирует `fanout=1`, который и так равен 1;
`--min-step-pages` в обеих командах = 2; отличается только `backprob` (0.5 / 0.7).
Измерено на 16 МБ: медиана скачка 641 и 429 страниц — обе конфигурации случайные.
Локальность даёт `-b 0 --min-step-pages 0`: медиана 20 страниц, 29% переходов
внутри одной страницы. На README-параметрах read давал 9.74 и 9.89 с.

### Не измерено
`perf stat` не собран: `kernel.perf_event_paranoid = 4`. Лечится
`sudo sysctl -w kernel.perf_event_paranoid=1`. Аппаратных счётчиков нет, выводы
опираются на page faults и переключения контекста из `/usr/bin/time -v`.

### Интрузивность — сильная часть работы
`/usr/bin/time -v` бесплатен: 12.10 против 12.18 с. `strace` не даёт read-версии
завершиться за 120 с (успевает ≈18%: 2 017 022 вызова `read` и столько же `lseek`
за 60 с), а mmap-версию почти не замедляет: 1.06 против 0.996 с. Под `stress-ng`
время растёт в 3–4 раза (34.1 против 8.96 с).

## 6. Воспроизведение

```bash
cd ~/projects/itmo-corp/study/os/os-course/lab/intro-exp

python3 ../util/graphgen.py -s 256M --seed 427 -o data/graph-rand.bin
python3 ../util/graphgen.py -s 256M --seed 427 --topology chain \
        -b 0 --min-step-pages 0 -o data/graph-seq.bin

gcc -o out/graph_traverse      src/graph_traverse.c      -Wall -O2
gcc -o out/graph_traverse_mmap src/graph_traverse_mmap.c -Wall -O2

sudo cpupower frequency-set -g performance
echo 1 | sudo tee /sys/devices/system/cpu/intel_pstate/no_turbo

# короткая демонстрация вместо полной серии
./scripts/collect.sh /tmp/demo.csv cold read 3 1 2
~/venvs/os/bin/python scripts/analyze.py /tmp/demo.csv --outdir /tmp/fig --warmup 0
```

Полный прогон: `collect.sh` четырежды (30/30/15/15), затем `intrusiveness.sh`,
`analyze.py` и `typst compile report/report.typ`. Около часа.
