# План ЛР2: LNX-4 VTKM (модуль ядра)

Вариант: **syscall, Linux header**. Интерфейс — системный вызов; целевая
структура задаётся именем из заголовков Linux. Конкретную структуру выбираем сами.

Задание: <https://github.com/secs-dev/os-course/tree/main/lab/vtkm>.
Вопросы к защите: вкладка «LNX-4: VTKM» в документе «Задания ОС 2026».

Код пишет Тимофей: по правилам курса ключевую логику нельзя писать через LLM,
промпты прикладываются к отчёту. Этот файл — разбор вариантов и порядок работы.

## Как устроена программа целиком

```text
./vtkm-cli 1234
   │  syscall(__NR_vtkm, 1234, &buf, sizeof buf)
   ▼
ядро: SYSCALL_DEFINE3(vtkm, ...)        ← пересобранное ядро, заглушка
   │  вызывает функцию, которую зарегистрировал модуль
   ▼
модуль vtkm.ko: PID → struct pid → struct task_struct
   │  копирует нужные поля в свою структуру ответа
   │  copy_to_user(buf, &ans, sizeof ans)
   ▼
vtkm-cli печатает ответ
```

Общий заголовок с форматом ответа (`struct vtkm_task_info` или подобный)
подключают и модуль, и программа: так у них одинаковая раскладка полей.

## 1. Какую структуру выводить

Требование задания: программа получает аргумент (не адрес), по которому ядро
через свои таблицы находит структуру.

| Структура | Аргумент | Как найти в ядре | Чем проверить вывод | Сложность |
|---|---|---|---|---|
| `struct task_struct` | PID | `find_get_pid` → `get_pid_task` (таблица PID) | `/proc/<pid>/status`, `ps -o` | низкая |
| `struct mm_struct` | PID | то же + `get_task_mm` / `mmput` | `/proc/<pid>/stat`, `/proc/<pid>/maps` | низкая |
| `struct vm_area_struct` (все VMA) | PID | `mm` + итератор VMA (maple tree с 6.1) под `mmap_read_lock` | `/proc/<pid>/maps` | средняя: ответ переменной длины |
| `struct inode` | путь | `kern_path` → `path.dentry->d_inode`, потом `path_put` | `stat <путь>` | низкая |
| `struct net_device` | имя интерфейса | `dev_get_by_name(&init_net, …)` / `dev_put` | `ip -s link` | низкая |
| `struct pci_dev` | `шина:слот.функция` | `pci_get_domain_bus_and_slot` / `pci_dev_put` | `lspci -nn -s …` | низкая, но в VM мало устройств |

**Выбор: `struct task_struct` по PID**, при желании с частью полей из `mm_struct`.

- Точно подходит под формулировку «из системных таблиц»: PID ищется в таблице PID ядра.
- Вывод легко сверить с `/proc/<pid>/status`, это удобно показать на защите.
- Затрагивает темы курса: процессы, планировщик (`prio`, `policy`), память (`mm`).
- Нужно разобраться с подсчётом ссылок (`get_pid_task` / `put_task_struct`)
  и RCU: это хорошие вопросы для защиты.

Поля для вывода (пример): `comm`, `pid`, `tgid`, PID родителя, `__state`,
`prio` / `static_prio` / `normal_prio`, `policy`, `nr_cpus_allowed`,
`utime` / `stime`, `nvcsw` / `nivcsw`, число потоков, из `mm`: `total_vm`,
`start_code` / `end_code`, `start_brk` / `brk`, `start_stack`.

Указатели ядра наружу не отдавать (адреса не выводятся, см. `kptr_restrict`):
только значения.

## 2. Как сделать системный вызов

Модуль сам не может добавить системный вызов в современное ядро:

- `sys_call_table` давно не экспортируется для модулей;
- с 5.7 не экспортируется и `kallsyms_lookup_name`, через которую таблицу находили;
- с 5.3 на x86 запись в CR0 закреплена (CR pinning), так что старый трюк
  «снять защиту записи и подменить слот» требует ассемблерных обходов;
- с 2024 года (6.9 и бэкпорты в стабильные ветки) x86-64 вызывает обработчики
  через `switch` в `x64_sys_call`, а не через таблицу, так что подмена слота
  в `sys_call_table` вообще ни на что не влияет.

| Способ | Как | Плюсы | Минусы |
|---|---|---|---|
| **A. Заглушка в ядре + логика в модуле** | В ядро добавить `SYSCALL_DEFINE3(vtkm, …)` и строку в `arch/x86/entry/syscalls/syscall_64.tbl`. Заглушка вызывает функцию через указатель, который модуль регистрирует при загрузке и снимает при выгрузке. | Честный способ, работает на любом ядре. Модуль можно пересобирать и перезагружать без пересборки ядра. | Ядро нужно один раз пересобрать. Надо продумать гонку с выгрузкой модуля (`try_module_get` или RCU). |
| B. Весь вызов в ядре, без модуля | То же, но логика целиком в ядре. | Проще всего. | Не выполнено задание: нужен загружаемый модуль. |
| C. Подмена слота `sys_call_table` из модуля | Найти таблицу через kprobe, снять WP, записать свой обработчик. | Без пересборки ядра. | На свежих ядрах x86-64 не работает (см. выше); хак, на защите будет трудно оправдать. |
| D. Перехват через kprobe / ftrace | Повесить обработчик на `__x64_sys_ni_syscall` и проверять номер вызова. | Без пересборки ядра. | Хак, зависит от деталей реализации ядра. |

**Выбор: способ A.** C и D стоит упомянуть в отчёте как рассмотренные и
объяснить, почему отказались: это сильный материал для защиты.

## 3. Окружение

Модули и ядро — только в виртуалке на `ssh home`, не на хосте: ошибка в ядре
кладёт систему.

Два пути, оба рабочие:

1. **Обычная VM с Ubuntu** (QEMU/KVM или VirtualBox). Исходники ядра той же
   версии, `make localmodconfig`, `make -j$(nproc) bindeb-pkg`, установить
   пакеты, перезагрузиться в новое ядро. Сборка с `localmodconfig` —
   порядка 10–30 минут на 12 потоках.
2. **virtme-ng** (`vng`): собирает ядро и сразу запускает его в QEMU поверх
   файловой системы хоста, без установки VM. Быстрее итерации, но ещё один
   инструмент, в котором надо разобраться.

Для начала хватит пути 1: он ближе к тому, как ядро ставят на настоящую машину.

## 4. Порядок работы

1. Подтянуть свежий курс, ветка `lab-vtkm` от `main`.
2. Поднять VM, поставить `build-essential`, `linux-headers-$(uname -r)`.
3. Собрать заготовку `lab/vtkm` (`make`), `insmod`, `dmesg`, `rmmod`.
   Понять каждую строку `vtkm.c` и `Makefile`.
4. В модуле: по PID найти `task_struct` и напечатать поля через `pr_info`.
   Параметр модуля (`module_param`) для PID — временно, для отладки.
5. Пересобрать ядро с заглушкой системного вызова, загрузиться в него.
   Проверить заглушку без модуля: должна возвращать `-ENOSYS`.
6. Регистрация обработчика из модуля, `copy_to_user`, коды ошибок
   (`-ESRCH` нет процесса, `-EFAULT` плохой указатель, `-EINVAL` размер).
7. Программа в user space: разбор аргументов, `syscall(2)`, печать полей,
   понятные сообщения об ошибках.
8. Тесты: свой PID, PID 1, несуществующий PID, PID потока, выгруженный модуль,
   сверка с `/proc/<pid>/status`.
9. Патч ядра положить в репозиторий (`git format-patch` или diff) рядом с модулем,
   чтобы проверяющий мог повторить.
10. PR, CI, ревью, отчёт, защита.
