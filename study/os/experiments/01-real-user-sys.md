# Опыт 1. real / user / sys — куда уходит время программы

Подготовительный опыт к ЛР intro-exp, курс «Операционные системы», ИТМО.
Тимофей Данилов, P3331.

Цель: научиться по трём числам от `time` понимать, чем программа была занята —
считала сама, работала в ядре или ждала устройство.

## Что означают три числа

- **real** — время по часам на стене. Секундомер: запустил — засёк, завершилась — остановил.
- **user** — процессор выполнял код самой программы (арифметика, циклы, работа с данными).
- **sys** — процессор выполнял код ядра, работая на эту программу. Не только по явному
  syscall: сюда же попадает работа ядра, которую программа не заказывала (page faults,
  обслуживание прерываний).

`user + sys` — всё время процессора, отданное программе.

**Главное правило:**

> Если `real` заметно больше, чем `user + sys` — программа **ждала**.
> Процессор в это время был свободен и работал на другие программы.

## Инструмент

`/usr/bin/time` (отдельная программа), а не встроенный в оболочку `time`. Причины:

- встроенный печатает по-разному в разных оболочках (zsh: `... 99% cpu ... total`;
  bash: три строки `real/user/sys`), для воспроизводимых замеров это плохо;
- встроенный не умеет ничего сверх трёх чисел, а нужны ещё page faults и пиковая память
  (`-l` на macOS, `-v` на Linux);
- встроенный — синтаксис оболочки, его нельзя обернуть в `sudo`, передать в `xargs` и т. п.

Мелочи, на которых можно споткнуться:

- `man time` показывает справку по `/usr/bin/time`; про встроенный — в `man zshbuiltins`.
  `man /usr/bin/time` не работает: `man` ждёт имя, а не путь, и пытается разобрать бинарник
  как исходник справки.
- суффиксы `dd` различаются: macOS понимает `bs=1m`, GNU/Linux требует `bs=1M`
  (`M` = 1024², `MB` = 1000², строчная `m` невалидна).

## Случай A. `sleep 3` — программа спит

**mac**

```
real 3.00   user 0.00   sys 0.00     (zsh: 0% cpu)
```

**home**

```
real 3.003   user 0.001   sys 0.003
```

`sleep` делает один syscall («разбуди через 3 с»), после чего ядро снимает его с процессора.
Программа не выполняется вообще — ей нечего выполнять. Секундомер тикает, процессор
работает на другие программы. `0% cpu` — прямое подтверждение.

## Случай B. Пустой цикл — чистый счёт

`bash -c 'i=0; while (( i < N )); do (( i++ )); done'`

**mac**

| N | real | user | sys |
|---|---|---|---|
| 300 000 | 1.63 | 1.41 | 0.20 |
| 3 000 000 | 18.07 | 15.57 | 2.34 |

`user` — основное число, `real ≈ user + sys` (1.41 + 0.20 = 1.61 против 1.63), 99% cpu.
Программа не ждала ничего, работала всё время.

`sys` (0.20 / 2.34) вырос ровно в 10 раз вместе с объёмом работы, то есть набирается
**по ходу цикла**, а не на старте процесса. Точная причина не измерялась — гипотезы:
работа аллокатора при перекладывании значения переменной и/или списывание на процесс
времени обработки таймерных прерываний. Проверяется подсчётом syscall'ов — тема опыта 2.

## Случай C. Чтение файла

Читаем `cat файл > /dev/null` — 200 МБ проходят через программу, но никуда не выводятся.

Промах: без `> /dev/null` вывод уходит в терминал, и меряешь терминал, а не чтение
(`real 4.66, user 0.00, sys 3.45` на маке).

У `cat` **`user` всегда ~0**: он ничего не вычисляет, только просит ядро переложить байты.

### mac, NVMe

| что | real | user | sys | зазор |
|---|---|---|---|---|
| 200 МБ из кэша | 0.03 | 0.00 | 0.03 | 0.00 |
| 200 МБ после `purge` | 0.07 | 0.00 | 0.04 | 0.03 |
| 2 ГБ из кэша | 0.29 | 0.01 | 0.27 | 0.01 |
| 2 ГБ после `purge` | 0.63 | 0.01 | 0.43 | 0.19 |

Зазор вырос пропорционально объёму. На NVMe ожидание есть, но скромное: ~30% времени.

### home

| что | real | user | sys | зазор |
|---|---|---|---|---|
| 200 МБ из кэша | 0.016 | 0.000 | 0.016 | 0.000 |
| 2 ГБ из кэша | 0.107 | 0.001 | 0.106 | 0.000 |
| 20 ГБ из кэша | 1.033 | 0.015 | 1.017 | 0.001 |
| 2 ГБ, вытеснен файлом на 42 ГБ | **15.199** | 0.009 | 0.552 | **14.64** |
| 2 ГБ, `drop_caches` перед прогоном | 1.02 / 1.09 / 0.97 | 0.00 | 0.27 / 0.38 / 0.23 | ~0.73 |

Строка с 15.2 секундами — контаминированный замер: чтение запускалось сразу после записи
42 ГБ, накопитель ещё дописывал хвост в фоне, наше чтение стояло в очереди за чужой записью.
**Вывод: нельзя мерить сразу после тяжёлой записи.** На спокойном диске те же 2 ГБ
читаются за ~1.0 с.

### Кэш страниц

Ядро держит в RAM копии недавно прочитанных кусков файлов. Отсюда «невозможные» скорости:

| объём записи (home) | скорость |
|---|---|
| 2 ГБ | 6.7 ГБ/с |
| 20 ГБ | 3.9 ГБ/с |
| 42 ГБ | 178 МБ/с |

Пока данные влезают в память — пишем в память и отчитываемся об успехе, не дожидаясь
накопителя. Как только кэш исчерпан, вылезает честная скорость устройства.
Чтение у этого SSD быстрое (~2 ГБ/с), длинная запись медленная (~178 МБ/с) — разрыв
в десять раз, типичный для дешёвых накопителей.

Один и тот же файл 2 ГБ на home: **0.111 с из кэша против 15.2 с с диска — в 137 раз.**

### Как сбрасывать кэш

```bash
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
```

- `sync` — дописать на диск dirty-страницы. Без него `drop_caches` выбросит только чистые
  страницы, часть файла останется в памяти, и замер выйдет смешанным.
- `3` — что выбрасывать: `1` кэш страниц, `2` кэш метаданных, `3` и то и другое.
- `tee`, а не `>`: перенаправление делает оболочка, уже без прав root.
- `/proc` — не файлы, а интерфейс к ядру. `drop_caches` работает как кнопка: запись =
  нажатие, состояние не хранится (чтение всегда даёт 0).

Это **действие, а не настройка**: кэш немедленно начинает наполняться заново. Значит
сбрасывать надо **перед каждым прогоном**:

```bash
for i in 1 2 3; do
  sync; echo 3 | sudo tee /proc/sys/vm/drop_caches > /dev/null
  /usr/bin/time -p cat /tmp/test2000.bin > /dev/null
done
```

Иначе первый прогон честный, остальные из памяти, и среднее по ним бессмысленно —
усредняются два разных явления.

|---|---|---|---|---|
| сон | 3.00 | 0.00 | 0.00 | ждёт по таймеру, снята с процессора |
| счёт | 18.07 | 15.57 | 2.34 | считает сама, 99% cpu |

## Шум машины: mac против home

Одна и та же работа, повторенная подряд:

| замер | прогоны | разброс |
|---|---|---|
| home, 2 ГБ из кэша | 0.107 / 0.109 / 0.109 / 0.108 / 0.111 | **~2%** |
| home, 2 ГБ с диска | 1.02 / 1.09 / 0.97 | **~12%** |
| mac, цикл 3 млн (5 прогонов) | 23.4 / 23.4 / 26.8 / 27.1 / 29.6 | **~27%** |

Мак с браузером и фоновыми задачами гуляет на четверть при одинаковой работе — эффект
в 10% там просто утонет в шуме. На простаивающей машине числа почти не шевелятся.
Отдельно: как только в дело вступает физическое устройство, разброс растёт (2% → 12%)
даже на спокойной машине — значит прогонов нужно больше.

Отсюда требование лабы к изоляции окружения: выделенная простаивающая машина,
фиксированный governor, отключённый Turbo, несколько прогонов.

## Контрольный вопрос

**Программе замерили `real 100`, `user 5`, `sys 3`. Чем она была занята и что бесполезно
делать для ускорения?**

Процессор работал на неё 8 секунд, остальные 92 она **ждала** — почти наверняка
медленное устройство, чаще всего диск.

Бесполезно оптимизировать код: переписать алгоритм, сменить язык, поставить процессор
быстрее. Всё это бьёт по тем 8 секундам; даже сведя их к нулю, получишь 92 вместо 100.

Работать надо с вводом-выводом: читать большими блоками, читать последовательно, а не
вразнобой, использовать кэш, взять накопитель быстрее.

## Связь с ЛР intro-exp

В лабе: **166 с real при 12 с user + sys** — 154 секунды (93%) ожидания NVMe.
Тот же профиль, что мы воспроизвели на home одной командой (15.2 против 0.56, 96%).
Программа не считает — она стоит в очереди к накопителю.

Почему в лабе 93% ожидания, а при нашем последовательном чтении ~70%: мы читаем файл
подряд, накопитель угадывает продолжение и подтягивает данные заранее. Лаба читает
вразнобой, предсказать нечего, каждый запрос ждёт по-настоящему. Разбираем в опыте 5.

## Терминологическое уточнение

**Major page fault** — процесс обращается к памяти, нужной страницы нет, ядро идёт за ней
на диск. Так работает `mmap`: файл отображён в адресное пространство, промахи выглядят как
обращения к памяти.

`cat` работает не так: он делает syscall `read()` — явную просьбу. Ядро видит, что данных
в кэше нет, шлёт запрос накопителю и **усыпляет процесс** до ответа.

Итог одинаковый (процесс спит, диск работает, процессор занят другими), механизм разный.
В лабе встречаются оба. Разводим в опыте 4.
